# Tool Advisor

Coordinate a scoped task using verified capabilities and a durable record. The current assistant is the coordinator; specialist files are instructions, not running agents.

**Before execution, present the specific combination and obtain the user's confirmation.** A broad build request or deadline does not confirm an unseen combination. Reuse an existing confirmation only for the same brief and proposal. This is the user's requested workflow. Small isolated edits and explanation-only questions take the ordinary direct path.

## Start or resume

Read `knowledge/BUILD-FLOW.md` in the configured research checkout **before choosing a route or recommending tools**. Its host overrides govern this skill. For Full discovery or an explicit deep comparison, breadth applies to research; minimality applies only to the final selection. An installed match is not a stopping condition. Use the proposal checkpoint in [discovery.md](references/discovery.md) before presenting a settled recommendation.

Locate the research checkout from the managed global instructions. Run the advisor installation check documented in that checkout's README; missing files or inaccessible research stay explicit gaps. Read the project ledger before planning resumed work. The bundled `scripts/ledger.py` is the local state tool; read [the command contract](references/ledger.md) before using it. The coordinator alone writes state. An existing project tracker remains the task source; link its IDs in task evidence.

## Interview

**For material missing or conflicting requirements, use grilling (Matt Pocock).** Invoke the available skill, or read its complete installed SKILL.md and explicitly use its interview instructions. Record whether use was native invocation or manual loading; a name in a plan is not execution. If needed but unavailable, report the missing dependency; do not claim Matt's interview ran. A complete brief does not require loading an interview skill or repeating answered questions.

Host adaptation: the coordinator looks up interview facts. Implementation workers start after combination confirmation; bounded read-only discovery workers follow BUILD-FLOW's pre-confirmation allowance. State this adaptation when using grilling, whose original instructions delegate factual research automatically. A host with no worker tools can still conduct the interview.

Use the supplied context to settle known branches. Read and extract all relevant provided materials first (text, code, attachments, images, diagrams, storyboards or specifications as applicable); do not require any particular document format. Differentiate exact requirements from illustrations, preserve detailed constraints and flag uncertain interpretation. Invoke the original Grilling method for meaningful missing or contradictory requirements, not answered questions. Capture goal, deliverables, constraints, success criteria, assumptions and open questions in the brief. Confirm the full interpretation in clear, ASD-STE100-inspired language for substantial work and persist the approved requirements in the project's existing authoritative document/tracker when a durable record is needed; avoid duplicate conflicting sources. A complete existing brief needs no repeated questions.

## Discover and propose

**Required skill: find-skills (Vercel).** Load it when entering discovery, then follow [the discovery contract](references/discovery.md). Search each necessary job across the repo, accessible installed capabilities and external sources. Read the full shortlisted instructions and supporting files at checked revisions. Source popularity and creator summaries are leads, not suitability verdicts. Repo review/install rules govern adoption. For substantial discovery, the coordinator may delegate bounded **read-only** research jobs to actual independent host workers *before* the implementation combination is confirmed, only under the limits in BUILD-FLOW; track source coverage, actual workers, and findings. Do not describe a shallow shortlist as completed research or dispatch execution workers before authorization.

Present the task-to-role mapping, sources/revisions, readiness, overlap, costs and gaps, including the intended agent assignments and independent review. A role is not proof that an agent ran. Save the brief, roles and dependency-aware task plan in the existing task record. When a ledger is used, show its proposal digest and record the user's actual answer with `confirm`; a self-authored approval is invalid. Wait for new confirmation only when the same scope and concrete combination have not already been approved. Material changes to scope or selected capabilities require a new proposal and confirmation.

## Coordinate and verify

After confirmation, prepare missing selected capabilities under the repo's inspection rules, record readiness evidence, and follow [the execution contract](references/execution.md). Match each confirmed task to its accountable role and selected skills, then delegate using the **current host session's native agent/worker tools** when available and authorized. Put the required skill sources, loading instructions and acceptance checks in the worker brief; a skill named in a prompt is not proof it was loaded. Do not build a separate dispatch adapter or assume that Codex and Claude Code expose identical tools. If dispatch or required skill loading is unavailable, report the limitation and use an approved sequential or alternative approach. Start only ready tasks with completed dependencies. Track real actors, blockers and results. Verify acceptance evidence before marking tasks done.

Finish only after all agreed deliverables are verified. Save a sanitized decision in the research repo with source revisions, results, failures and user corrections. Keep raw project state local. Proposed reusable improvements from project failures must pass the [cross-project scope and independent-review gate](../../../docs/WORKFLOW-CHANGE-REVIEW.md) before shared/global adoption; do not assume a Nullement-specific fix is universally beneficial. Instructions and a ledger support this process; they do not guarantee host obedience or universal discovery.
