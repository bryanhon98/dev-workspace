# From a build request to a useful skill combination

The assistant in the current conversation is the **advisor**. This repo supplies its playbook, source catalog and dated decisions. Specialist skills supply instructions for particular jobs; they are not extra trained brains. A separately installed Agency agent or an ECC controller is not required to start.

## When to start

Use this flow for a substantial new website/app, redesign, complex feature, or explicit request to choose tools. Start even when the user names no skills. Read the project and conversation first. For a small typo, isolated fix or explanation-only question, use the relevant existing context without a broad interview or tool search. An assessment request does not authorize building the assessed product.

The root and global AGENTS.md files point here. They work when the host loads those instructions; this repo does not intercept every prompt. Updating the global source here does not update a laptop's installed instructions. Outside this checkout, use a known accessible checkout or the [GitHub source](https://github.com/bryanhon98/dev-workspace); if unavailable, state that the stored playbook/decisions could not be consulted. Never claim universal discovery or guaranteed routing.

## The six steps

1. **Understand the job.** Extract the goal, audience, desired experience, must-have features, available assets, stack/device constraints and success criteria. Ask only about missing details that change the work, normally one to three focused questions per round. Do not ask again for answers already in the conversation or project. A short brief with stated assumptions is enough for reversible work; pause only the work that depends on a genuinely required answer. Offer a deeper interview when the user wants it or unresolved complexity warrants it. Do not force an exhaustive interview on every request.
2. **Map the jobs.** Turn the brief into capability needs and consult all matching [routes](ROUTING.md). For the book/shirt website: visual direction, book/page choreography, realistic assets/materials, web 3D, inspect-versus-scroll controls, accessibility and performance. Record the necessary jobs before choosing favorite tools.
3. **Find and read candidates.** Follow [ADVISOR.md](ADVISOR.md): check accessible installed capabilities, repo inventory, prior decisions and research; search each missing job separately. Read the complete relevant installed and current upstream instructions plus supporting files, record exact revisions and distinguish source review from working-device evidence. Find Skills can be one external discovery channel. ECC scout/stocktake/search-first supply useful methods; the repo already has a scoped read-only inspector. A full device audit is needed for setup comparisons, not for every small feature. Account for plausible alternatives even when the user did not name them.
4. **Choose the smallest combination.** Assign one owner to each job and explain overlap. Usually keep one development workflow and one design director, adding a motion/3D/testing specialist only where needed. Give a compact fit table: job, selected capability, reason, deferred alternative and gap. Separate a library/runtime from a guidance skill. A specialist may be used by the current assistant; selecting a role does not require spawning another agent. Delegation remains subject to the host's and user's instructions.
5. **Do the authorized work and verify it.** A build request authorizes progress on the build; a recommendation-only question calls for advice. Continue within that scope without adding a ritual approval step after the shortlist. New skill installations, replacements, removals, external publishing and account setup retain their existing authorization and inspection rules. Test the actual user journey and relevant project checks. For the book example, verify page flipping, model loading, inspection/control handoff, continuation to the next object, mobile input, reduced motion and measured rendering performance.
6. **Save evidence and improve.** Record the chosen roles, exact sources, gaps, observed outcomes and user corrections in a dated [decision](decisions/README.md). A recommendation is not a successful trial; an unknown result stays unknown. Reuse these records next time, refreshing sources relevant to the new task. Learning here means maintaining evidence and rules, not training model weights or running background surveillance.
