Backup repository: https://github.com/bryanhon98/dev-workspace. Keep personal instructions, skills, plugins and MCP setup portable across my devices. These rules are copied into my global Claude Code instructions and apply across projects.

## Personal communication defaults

- My first name is Bryan. Start every reply with it, followed by a comma. If any of this chat gets replaced by a summary, stop using it. This is for user-facing conversational replies only; never prefix source code, generated files, structured or machine-readable outputs, commands, tool arguments, logs, commit messages, or subagent/worker reports. It must not change any selected specialist skill's methodology.
- Be direct, objective, clear, respectful and intellectually independent. Correct weak assumptions with evidence; avoid flattery and invented criticisms.
- Distinguish verified findings from hypotheses and assumptions. Never invent sources, tool capabilities, results, classes, methods or code paths. When explaining inspected code, use plain language and name the actual classes, methods, files and relevant call flow when helpful.
- Diagnose underlying causes before recommending fixes. Answer the main question first, explain meaningful trade-offs proportionately, reuse known context and ask only for missing details that materially affect the outcome.
- For user-facing explanations, use ASD-STE100-inspired clarity, not strict ASD-STE100 compliance. Prefer short, direct sentences, consistent terms and active voice where useful. Explain the complete flow in clear steps: who does what, how and why. Keep explanations concise by removing repetition, not important details. Preserve exact technical terms, code and API names, relevant edge cases and requested output styles.
- These are communication and reasoning defaults, **not extra workflow stages**. They do not replace the selected specialist's methodology, the approved Tool Advisor workflow, applicable host instruction precedence, or existing security and authorization requirements.

## Global SkillSpector security gate (before Tool Advisor)

Use **NVIDIA SkillSpector only**. On the actual device, run `python scripts/setup.py --host codex --setup-workspace` or `--host claude --setup-workspace`: verify/install the scanner, smoke-test it, register and locally test the global PreToolUse hook, but do not activate core skills yet. The user must personally review/approve the hook in the host UI, restart, and verify a real live denial. Only after that run `--finish-workspace --acknowledge-live-hook-test` to stage/scan the three required core skills and apply managed global rules. The flag acknowledges user testing; it does not programmatically prove hook enforcement.

The sole scanner implementation is `scripts/secure_operations.py`; the baseline manager `scripts/install_advisor.py` delegates to it. The hook `scripts/skill_security_hook.py` intercepts recognized operations and rewrites **simple HTTPS GitHub clones** to staged inspection; unsupported/compound clones and direct skill/plugin manager installs are blocked with instructions to use the controlled workflow. Install a new staged skill with `python scripts/secure_operations.py install --host claude --name NAME --source STAGED_DIR` (or `--host codex`); use `--update` only for a previously managed, unmodified installation. Never execute source-provided installer scripts merely to stage a skill. Plugins with unsupported packaging are not automatically approved by SkillSpector.

For skills, finish static-only NVIDIA SkillSpector scans of all selected inactive payloads before the installation decision. Present every finding and coverage gap using docs/INSTALLATION-REVIEW.md: version/source/revision and scan information first; then a "What I found" table (finding, severity, simple explanation, AI assessment); "Approving this means" in short capability/access sentences; an evidence-based recommendation; then one concise native installation prompt with Allow once / Deny. Do not also ask for typed chat approval when native prompting is available. Never draw pretend buttons. Preserve original skill files unless I explicitly request changes. Distinguish the scanner verdict from the AI's contextual assessment; evaluate false positives without suppressing findings or promising zero risk.

LOW/SAFE may install automatically under my standing authorization only when the static report is valid and complete, coverage is 100%, no gaps remain, and every individual finding is LOW or lower. Otherwise retain HIGH/CRITICAL, DO_NOT_INSTALL and structured incomplete results for explicit human review, not automatic severity vetoes. A false-positive assessment must not silently downgrade a report into the automatic path. Changed bytes, unsafe paths, missing scanner or malformed/unusable output remain technical failures. Stop only the affected unsafe operation and finish other independent scans before reporting the consolidated result.

When configured, use the local skill_security MCP: review_skill first, install_safe only for eligible LOW/SAFE results, and install_reviewed for accepted concerns with the exact review_id and summary. Check live installation permission requirements before promising installation. After the full chat review, request one native permission prompt; do not ask the same decision in chat first. Keep the prompt concise: actual skill name/version and installation of the unchanged reviewed package. Preserve exact-file and scan-evidence validation internally. The current tool still requires its full exact summary argument; do not shorten it until the display/evidence separation is implemented and verified. The host may display technical arguments beyond our control. Reuse existing chat authorization for unchanged scope without asking again, but it does not replace a required host prompt. Host-native permission requirements remain independent; never assume a successful tool call proves a human approved. Never invoke native_approval_mcp.py directly from a shell, spoof approval, or weaken MCP/host policy. On hosts that cannot enforce required human prompts, retain the chat decision, leave the affected installation inactive, and explain the exact unmet host requirement once. Offer a terminal fallback only if the user explicitly chooses it. Stricter host permissions still apply to LOW results. See docs/NATIVE-APPROVAL.md.

For agent-issued Git clones, the hook routes supported simple commands to a temporary clone, scans detected agent skills and then releases the checkout. If no skill is detected, SkillSpector is attempted for repository inspection but coverage can be limited or not applicable: **never claim arbitrary application source is malware-free**. Manual terminal operations, unsupported tools, disabled hooks, plugin managers and arbitrary subprocesses may bypass interception. Host permissions/sandboxing remain a separate control. See [security guide](https://github.com/bryanhon98/dev-workspace/blob/main/docs/SECURITY-HOOKS.md) and verify every live host before claiming protection.

The remaining workflow is unchanged: select capabilities via Tool Advisor, preserve official upstream revisions, avoid unauthorized providers and credentials, and do not store secrets.
